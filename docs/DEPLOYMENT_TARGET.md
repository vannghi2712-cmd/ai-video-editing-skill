# Deployment Target — Proposed Cloudflare Architecture

> This document describes an intended future target architecture for human review and approval only.

---

## 1. Overview

The `auto_video_editor` pipeline is currently designed as a local-first CLI tool. This document proposes a future split-plane architecture where a **web control plane** (Cloudflare Workers + Pages) coordinates work dispatched to a **Python compute plane** (long-running VMs or container workers) that executes FFmpeg, Whisper, and AI inference.

This separation exists because:
- Cloudflare Worker CPU and memory limits depend on the current platform plan and configuration. This proposed architecture must not depend on a hard-coded runtime limit. Current limits must be verified from official Cloudflare documentation during the deployment phase.
- Direct-to-R2 uploads avoid buffering full video files through Worker memory.

## 3. Direct-to-R2 Uploads

**Problem:** Routing raw video through Cloudflare Standard Workers is infeasible — a 500 MB clip would exhaust the 128 MB memory limit.

**Proposed solution:** Short-lived R2 presigned upload URLs generated by the control-plane Worker.

**Proposed flow:**

1. Browser requests a presigned upload URL from the control-plane Worker (authenticated).
2. Worker calls the R2 API to generate a short-lived (e.g., 15-minute) presigned `PUT` URL.
3. Browser uploads directly to R2 — Worker is not in the data path.
4. R2 `onUploadComplete` hook (or polling) triggers the compute job.

> **UNVERIFIED:** R2 presigned URL support and `onUploadComplete` hook availability should be confirmed against the [Cloudflare R2 documentation](https://developers.cloudflare.com/r2/) before implementation.

## 4. Metadata Store (D1) and Orchestration

| Component | Proposed Technology | Purpose |
|---|---|---|
| Job metadata | Cloudflare D1 (SQLite) | Store job state, profile used, timestamps, output paths |
| Job queue | Cloudflare Queues | Decouple control plane from compute plane |
| Long-running jobs | Cloudflare Workflows (beta) | Durable multi-step orchestration with retries |
| Object storage | Cloudflare R2 | Store raw uploads and rendered outputs |

> **UNVERIFIED:** Cloudflare Workflows is in beta as of the time of writing. Confirm GA status and limitations at [developers.cloudflare.com/workflows](https://developers.cloudflare.com/workflows/) before using in production.

## 5. Proposed GitHub Workflow

```
feature/my-change
       │
       ▼
  Pull Request → CI (lint, tests, pyproject.toml build check)
       │
       ▼  (PR approved and merged to main)
  main branch → Deploy: Cloudflare Pages (frontend)
                       + Workers (API)
                       + D1 migrations
```

**Rules:**
- No secrets committed to Git. All credentials via Cloudflare environment variables or Wrangler secrets.
- `wrangler.toml` committed only with non-sensitive configuration (account ID is not a secret; API tokens are).
- Branch protection on `main` — direct push prohibited.
- All D1 migrations versioned and applied via CI, not manually.

## 6. Security Requirements

| Requirement | Detail |
|---|---|
| **CSRF protection** | All state-mutating API routes require CSRF token (double-submit cookie or signed header pattern) |
| **Tenant isolation** | Each user's R2 objects scoped under `users/{user_id}/jobs/{job_id}/` — no cross-user path access |
| **Upload quotas** | Per-user file size and daily job count limits enforced at presigned URL generation time |
| **Authentication** | Cloudflare Access or a JWT-based session layer — no unauthenticated job submission |
| **Signed output URLs** | Rendered outputs served via short-lived presigned R2 `GET` URLs, not public buckets |
| **Content validation** | MIME type and magic-byte checks before accepting an upload as a valid video file |
